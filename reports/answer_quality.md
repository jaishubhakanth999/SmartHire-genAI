## 5. Prompt iterations (before/after)

**Change:** the mentor's system prompt was tightened from a loose
"answer using context if relevant" instruction to an explicit scope
restriction with a mandatory refusal instruction (see
`MENTOR_SYSTEM_PROMPT` in `src/generate/prompts.py`).

**Test question (off-topic, not career-related):** "What is the capital of
France?" -- run against the live pipeline with both prompt versions, same
retrieved context, same LLM call:

| | Before (loose prompt) | After (`MENTOR_RAG_PROMPT`, current) |
|---|---|---|
| Prompt | *"You are a career mentor. Answer the user question using the context below if it is relevant."* | *"...answer career questions...using ONLY the retrieved context...Stay strictly within career-guidance topics; politely decline anything else."* |
| Answer | "Based on the information available to me, the capital of France is Paris. The context provided focuses on career guidance...and it does not contain information relevant to your specific question." | "I don't have that in my documents. My scope is strictly career-guidance topics...so I can't help with general knowledge questions." |
| Verdict | **Fails** -- answers from the model's own general knowledge instead of declining on scope. | **Passes** -- declines cleanly, states its scope, offers to help with a career question instead. |

This is exactly the failure mode the spec's guardrails requirement (section
5) targets: without an explicit scope instruction in the prompt itself, the
model happily answers off-topic questions from its own knowledge, which
defeats the point of a RAG-grounded, scope-limited mentor. The fix was prompt
engineering, not a guardrails regex -- guardrails.check_input() intentionally
does not hard-block "off-topic" questions with a keyword list (too brittle,
see the comment in `src/safety/guardrails.py`), so scope enforcement has to
come from the prompt + the LLM's instruction-following.
